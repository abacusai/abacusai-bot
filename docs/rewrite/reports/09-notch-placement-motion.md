# Notch placement and motion

This change supersedes the placement and resize-animation decisions in report 08. Implementation research was refreshed on 2026-10-07. No third-party code was copied.

The native window reserves the maximum 560 × 220 point shape, plus the existing transparent margins, when it is created. Presentation changes update visibility and audio eligibility without changing native or child-view bounds. Display configuration changes can reposition the envelope. The director sends one final report and no longer waits for CSS transition events or requests intermediate envelope sizes.

On macOS every display anchors at `display.bounds.y`, including external and non-notched screens. Hardware safe-area and auxiliary-area measurements, fractional camera center compensation, and the empty camera column remain intact. Windows centers the envelope at the display top and reserves a top taskbar using that display's work area. Side and bottom taskbars do not move it. Both platforms honor `prefs.notch.extraDisplays`.

Motion animates numeric shell dimensions with a 300 ms spring and 0.1 bounce, then maps those values to a centered CSS path clip inside the fixed envelope. Hardware layouts have inward top shoulders and round bottom corners. No-notch layouts have rounded capsule corners and no camera spacer. Content lays out at its destination size without scaling text or the camera column. Wings fade after the shell settles; body controls follow by 50 ms. Both remain hidden during resizing so their destination layout cannot flash through a smaller clip. Reduced motion uses immediate shell changes. Hover opens after 120 ms and closes with 300 ms grace. Replies, approvals and typing remain interactive across pointer leave.

Forwarded pointer movement uses Chromium's clipped `elementFromPoint` result to choose native click-through. Transparent margins and clipped corners do not start hover. Native hover interaction no longer changes focusability or blurs a typing session. Input pointer-down and focus request both the panel's key focus and its active web contents. Escape, submission and collapse release focus when a typing session has acquired it. Passive hover collapse does not blur the panel or change its focusability. The existing macOS non-activating panel, screen-saver level and all-Spaces/fullscreen behavior remain in use.

## Reference notes

- [DynamicNotchKit](https://github.com/MrKai77/DynamicNotchKit/tree/main/Sources/DynamicNotchKit), MIT: `DynamicNotch/DynamicNotch.swift` reserves a transparent panel at the display's top; `Utility/DynamicNotchPanel.swift` allows key focus without ordinary app activation and sets screen-saver/stationary/all-Spaces behavior. `DynamicNotch/DynamicNotchTransitionConfiguration.swift` documents a 300 ms spring and direct compact/expanded conversion. Those ideas informed the fixed envelope and spring.
- [boring.notch](https://github.com/TheBoredTeam/boring.notch/blob/main/boringNotch/ContentView.swift), GPL, ideas only: `ContentView.swift` uses a shared interactive spring with response 0.38 and damping 0.8, cancellable hover tasks, and a 100 ms leave grace. Separate open/close springs use 0.42/0.8 and 0.45/1.0. The lesson is one interruptible shell animation and deliberate hover timing, not simultaneous native/CSS resizing. No GPL implementation was copied.
- [NotchDrop](https://github.com/Lakr233/NotchDrop/blob/main/NotchDrop/NotchWindow.swift), MIT: transparent, shadowless window, elevated status-bar level, stationary/all-Spaces/fullscreen auxiliary behavior. Its measurement code reinforces per-display coordinates.
- [Notchmeister](https://github.com/chockenberry/Notchmeister/blob/main/Notchmeister/Notchmeister/NotchExtensions.swift): `NotchExtensions.swift` measures a fake notch using the individual display and its menu-bar reservation. Its decorative spring effects are not appropriate timing targets for reply controls.
- [Alcove](https://tryalcove.com/) presents compact live activities with fluid transitions. [MediaMate](https://wouter01.github.io/MediaMate/) emphasizes compact HUDs and support across Macs. Their product pages do not expose spring parameters or native implementation details.
- [Look Alive](https://www.lookalive.app/) describes agent faces, decision prompts, replies in the notch and a pill on external displays. That supports a compact companion with usable reply controls on either display type. Its site was readable via HTTP after the browsing tool failed.
- [NotchNook](https://lo.cafe/notchnook) was requested as a reference, but its vendor page returned HTTP 502. No claims about its internal animation or window implementation are inferred from marketing or third-party reviews.

## Final spacing and floating placement correction

This section supersedes the earlier flush placement and 16/12/14 spacing choices for floating mode. Hardware placement remains flush with the bezel.

Three native LG trials compared inline/top/bottom insets of 10/8/8, 12/8/10 and 12/10/10 points. The first trial used a 6-point top gap; the others used 8 points. The 10/8/8 focused reply left only 4 points between its focus outline and the lower curve. The 12/10/10 trial added header height without improving corner clearance. **The final content tokens are 12 inline, 8 top, 10 bottom, with a 6-point item gap.** The fixed 28-point icon hit targets remain. The reply pill has a 4-point control inset; its text padding is derived so text starts 12 points inside the pill in either layout. Hardware nominal side padding adds the 12-point shoulder inset, so content is still 12 points from the painted vertical edge. Camera clearance is 12 points on either side of the measured cut-out, with the existing safe-area/auxiliary-area measurement unchanged.

The prior edge contact was direct: `notchPlacement` returned the display's top y for both modes, and the capsule clip started at local y=0. The fixed envelope had side and bottom margins but no top offset. Floating placement now returns `bounds.y + 8`, centered on the display, including notchless Macs, external displays and Windows top-taskbar configurations. It deliberately stays in the top system band rather than following `workArea.y`. Hardware placement still returns `bounds.y`. Floating maximum shape dimensions also shrink for small displays, keeping all painted edges inside the display at maximum expansion, with one fixed envelope across states.

The floating path has four convex corners and a compact half-height radius. A `drop-shadow(0 4px 6px rgb(0 0 0 / .24))` on the transparent parent follows the clipped silhouette; it does not draw a rectangular native window shadow. Hardware shoulders remain concave and have no floating shadow. The native window keeps `hasShadow: false` and `roundedCorners: false` so its envelope cannot add another outline or clip the shape.

New native captures show an 8-point background band above every floating state. A pixel scan finds the first black center pixel at row 16 on the 2× screenshots for all five floating states, versus row 0 for every hardware state. The selected content spacing measured 12 points minimum inline and 10 points minimum bottom in expanded idle, reply, approval and listening. The input's outer focus outline remains clear of the bottom curve. Native motion recording held x=976, y=8, width=608, height=252 throughout repeated expansion/collapse. The new reduced-motion test exposed the transformed clip being scheduled one frame after its content bounds; reduced mode now commits a literal path in the same render, and the real Electron harness passes.

macOS exposed only the LG ULTRAWIDE, with no built-in display available. A separate audit instance launched with `ABACUSBOT_NOTCH_METRICS=185x33` exercised the native dev-metrics path on that display. The native panel moved to y=0, and the renderer reserved a 209-point camera exclusion, 185 camera plus 12 clearance on each side. Its captures show the hardware shoulders meeting the top edge and no capsule shadow. These are simulated hardware screenshots, not evidence from a physical camera cut-out.
