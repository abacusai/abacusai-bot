1. **Blocker. §3.5.6 says browser auto-allow calls `respondPermission()` synchronously.** Both sessions emit `permission_needed` before registering the waiter. The synchronous answer therefore finds no pending entry and disappears; the tool waits until timeout. See [session.ts](/Users/rajaniraiyn/work/abacusai-bot/packages/agent/src/session.ts:2734) and [bot-session.ts](/Users/rajaniraiyn/work/abacusai-bot/packages/agent/src/bot/bot-session.ts:1428). **Fix:** preserve asynchronous delivery after waiter registration, including the existing post-Stop suppression. Add an auto-allow round-trip test.

2. **Blocker. §3.1 opens a zero-length run for input received while busy.** The original run is still open, contradicting `runs.open()` throwing on overlap and §7.3’s prohibition on another `RUN_STARTED` before the terminal. There is also an admission race while opening a run awaits `setModel()` before `runTurn()` sets `busy`. **Fix:** reserve admission synchronously and define a queue acknowledgement that does not open another run. Test concurrent input during model selection and active streaming.

3. **Blocker. §3.5.3 claims permissions from previous processes are stale.** Permission IDs restart at `perm-1`; `respondPermission()` checks only that ID. An old response can match a different permission in a replacement process. The resume algorithm specifies no explicit lineage validation before applying decisions. **Fix:** validate thread, interrupted run, process incarnation and pending batch before calling the session. Reject mismatched lineage without answering any permission.

4. **Major. §3.5.3 closes an unmatched resume successfully and says this clears pending items.** That clears ChatClient’s interrupts even when the current pi turn still awaits valid permissions. The client then has no prompt with which to unblock the turn. **Fix:** retain the current pause on stale submissions. Return a correlated submission error or re-emit the authoritative pending descriptors; never report successful completion of an unanswered pause.

5. **Major. §3.5.1 adopts all-or-nothing permission batches while declaring approval behavior unchanged.** `InterruptManager.maybeSubmit()` waits until every owned item is staged. Today, each `permission_response` immediately releases its individual waiter. Approving one tool while leaving another unanswered therefore changes execution timing and ordering. A 25 ms batching window does not remove that difference. **Fix:** preserve independent permission responses through an explicit control path, or obtain a separate behavior-change decision. Test that an approved sibling executes while another permission remains pending.

6. **Major. §3.5 and PLAN.md claim generic-bound permissions render inline through `ToolProps.interrupt`.** The binding is accepted, but `ai-client/src/ui/selectors.ts:100–138` associates only `kind:"tool-approval"` items with tools. Generic items remain in the interrupt slot. A real reference ChatClient probe produced one resolvable generic interrupt, so duplicate native/legacy items are not the demonstrated problem. **Fix:** explicitly join generic permissions to tool widgets by `toolCallId`, or implement the complete tool-approval binding and client-tool registration contract.

7. **Major. PLAN.md encodes decisions and rules with `resolveInterrupt(approved, {payload})`.** The proposed generic handle accepts one payload argument. Passing `true` sends a boolean, which §3.5.3 does not map to acceptance. The proposed native tool-approval alternative also nests custom data under `payload`, while the host expects top-level `decision` or `answers`. **Fix:** specify one exact envelope for each decision and update the plan and widgets. Test every decision through the actual bound handle, including allowance rules and question answers.

8. **Major. §3.5.5 treats `CUSTOM approval.cleared` as retiring an interrupt.** ChatClient’s interrupt manager changes from interrupt terminals, hydration and resolutions; this custom name does not remove an item. When one item in a batch expires, the spec waits for the last expiry before opening a continuation. The expired item remains in the client’s completeness gate. **Fix:** reconcile the pending batch on every expiry, including newly bound descriptors and staged surviving decisions. Test one expiry with another permission still actionable.

9. **Major. §3.5.2 buffers sibling events, and §3.5.5 discards them on cancellation.** A sibling can finish successfully before Stop while another tool awaits approval. Today its result reaches artifact extraction immediately. Under the proposal, cancellation discards that already-completed result and its artifact record. Child text and routine text can disappear similarly. **Fix:** deliver tap-relevant events immediately through an ordered compatibility channel, even if chat rendering buffers them. Test “sibling creates artifact, then Stop during permission.”

10. **Major. §3.3.2 encodes tool failures solely as `ToolResultContent.isError`.** StreamProcessor does not interpret that JSON property as its error state. Its result handler checks `metadata.tanstack.state === "output-error"` or `toolResultOutcome`. A processor probe rendered the proposed rejected result as `state:"complete"`. **Fix:** emit the recognized error metadata, with denial/cancellation outcomes where applicable, while retaining the legacy text and rejection flag.

11. **Major. §3.1 settles subagents before settling their outstanding tools.** It emits `SUBAGENT_ERROR` first, then tagged synthetic tool results. `StreamProcessor.routeToChild()` drops subsequent events for an errored child. Those tool results never reach the child transcript. **Fix:** finish child messages and settle child tools before emitting the subagent terminal. Assert the resulting child parts, not just stdout ordering.

12. **Major. §3.8’s settlement guard is not owned by a particular turn.** Every `session.send()` finally calls an unqualified `runs.settle()`. A superseded send can finish after Stop has started the next run and settle that newer run. Added `turn_settled` events can also arrive while `stop()` is awaiting abort, before the controller records cancellation. **Fix:** bind settlement to an immutable turn/run token, mark cancellation before awaiting abort, and ignore settlement from superseded owners. Test deferred abort with immediate replacement input.

13. **Major. §3.2 infers terminal `model_unavailable` from whether streaming has started.** A failed `forwardedProps.model` application occurs before streaming, so it is classified as terminal even if the existing model successfully answers afterward. The mapping table separately calls `setModel()` failures non-terminal. **Fix:** classify by the producing operation or explicit internal failure category, not a status heuristic.

14. **Major. §3.1 deduplicates by the newest user message ID.** ChatClient’s `reload()` retains that user message and submits a fresh run to regenerate its answer. The proposed host instead closes successfully without prompting. Retrying a failed request with the same message ID is also suppressed. **Fix:** deduplicate transport retries by request/run identity, and define regeneration explicitly. Do not treat a reused user message ID as proof that a new run is redundant.

15. **Blocker. §§3.2, 4 and 5 replace idle-then-error with one failure terminal while claiming messaging parity.** [MessagingGatewayService](/Users/rajaniraiyn/work/abacusai-bot/apps/desktop/src/main/services/messaging/messaging-gateway-service.ts:1209) deliberately ignores provider failures arriving after idle because the reply already ended. The proposed terminal path appends that failure and sends it remotely. `feedTurnWaiter()` likewise currently resolves on idle before a late error. **Fix:** preserve the existing tap event ordering and decisions independently of ChatClient’s terminal lifecycle. Test actual remote reply content and waiter resolution against the baseline.

16. **Major. §5 tells messaging, routine and waiter taps to consume all `TEXT_MESSAGE_CONTENT`.** §§3.1 and 3.3.2 also emit user text for dequeues and steers. Content events have no role, so the proposed taps append the user’s own input to the agent’s reply. **Fix:** track roles from `TEXT_MESSAGE_START` and consume assistant-originated content only. Cover both steered and dequeued user messages.

17. **Major. §§3.3.4 and 7.1 do not preserve legacy message-boundary semantics for child text.** Delegate/document/deck/design final text currently has no `messageId`. Giving it a new child message ID makes the messaging gateway reset its reply buffer. Prefixing browser message IDs also changes equality across child invocations. “Preserving equality classes” does not preserve the distinction between an absent ID and a present one. **Fix:** retain the original legacy ID, including absence, in compatibility metadata and use it for taps.

18. **Major. §3.3.5 tracks announcements globally by `toolCallId`, but §3.3.7 retains kind-prefixed child IDs.** `forwardChildToolEvents("sub", …)` namespaces by child kind, not invocation. Two independent delegates can produce the same `sub-<provider-id>`. A global announcement/result map can suppress or misattribute the second child’s call. **Fix:** key emitter bookkeeping by both `subagentRunId` and `toolCallId`. Test parallel children deliberately reusing provider IDs.

19. **Major. §3.3.2 emits `replace /plan` although `AgentState.plan` starts absent.** RFC 6902 `replace` requires an existing property. The proposed first successful todo update violates §7.3’s clean-patch property. Also, `setTodos()` trims content, so copying tool arguments does not necessarily reproduce stored state. **Fix:** use `add` for the first assignment and publish the normalized successful todo state. Test absent, empty and whitespace-normalized plans.

20. **Major. §3.7 says main strips every host-service `TOOL_CALL_*` by `toolCallName`.** Only `TOOL_CALL_START` contains that name; args and end events do not. Filtering each event literally leaks payloads into the renderer/ring and leaves unmatched events after removing the start. **Fix:** maintain a set of host-service request IDs and filter all corresponding events by ID. Test interleaved host requests and ordinary tools while interrupted.

21. **Major. §3.3.5 describes pi’s streaming shapes incorrectly.** In both installed pi 0.85.1 and reference 0.99.1, `toolcall_start` and `toolcall_delta` contain `contentIndex` and `partial`; only `toolcall_end` contains `toolCall`. Reading `event.toolCall` for the first two loses IDs and streamed arguments. **Fix:** extract the tool block from `partial.content[contentIndex]`, guard incomplete blocks, and handle the final event separately. Test actual provider event shapes, not invented internal fixtures.

22. **Major. §3.8 adds an agent-side watchdog that calls `session.stop()`.** The current standalone host has no such timeout. This adds a new abort policy in AG-UI mode, contradicting “only the wire” and unchanged heartbeat/stop behavior. Passing NDJSON goldens cannot detect it. **Fix:** keep watchdog policy in the existing host/main layer for this slice. Treat a standalone watchdog as a separately authorized behavior change.

23. **Major. §§5 and 8.3 make snapshot recovery conditional on whether live interrupts require `MESSAGES_SNAPSHOT`.** The reference ChatClient round trip works without that event. The unresolved case is a fresh client or truncated replay ring: tool-result fallback requires an existing tool part, and tagged child events are dropped unless the corresponding subagent card exists. A bounded ring cannot necessarily reconstruct either. **Fix:** require authoritative transcript and interrupt hydration, plus an explicit replay-gap protocol. Test reload, second-window attachment and ring eviction during an interrupted child run.

24. **Major. §§2.3 and 7.6 claim the declared string-discriminator types are assignable to canonical event types.** Installed `@ag-ui/core@1.0.0` and reference TanStack types use `EventType` enum members; plain `"RUN_STARTED"` literal types are not assignable to those enum members. Also, §6.3 adds `@tanstack/ai` but omits `@tanstack/ai-client`, which §7.4 needs for ChatClient tests. **Fix:** derive enum-compatible declarations through type-only imports or checked constructors, add the exact client test dependency, and make conformance compile without casts.

25. **Minor. §§2.3 and 3.3.5 recompute tool title/kind metadata on `TOOL_CALL_END` and expect it to reach the UI.** StreamProcessor reads canonical input there but retains metadata captured on `TOOL_CALL_START`. A processor probe kept the old title after receiving the proposed updated title. **Fix:** specify a client-consumed metadata update mechanism or update the tool widget from the application’s display-event store. Assert final rendered metadata, not only emitted END metadata.
