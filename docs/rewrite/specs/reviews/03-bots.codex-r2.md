1. **Major — §5.3 assumes hover preloading cannot render an unready chat.** The preload loader returns a successful result containing a possibly null `sessionId`, without `workspaceId` or hydration. Foundation’s `defaultPreloadStaleTime: 0` causes reloading, but the router clone’s `load-client.ts:837–850` reloads successful matches in the background by default. Clicking after hover can therefore mount §11.1 with the preload result before `openChat` finishes. **Fix:** use a blocking stale reload for these routes, or await enter-only readiness in `beforeLoad`. Extend R3-T3 with hover followed by click while opening and hydration are delayed.

2. **Major — §24.12 assumes live AG-UI messages have a “dual-written v1 transcript.”** The implemented [TranscriptService](/Users/rajaniraiyn/work/abacusai-bot/apps/desktop/src/main/services/session/transcript-service.ts) writes v1 and derives v2 from it. The agent spec’s §5.3 instead persists AG-UI directly as v2; neither defines the reverse writer assumed here. An ID alias cannot make `DebugSyncService` upload a segment that does not exist. `botChatPreview` and its `onPersist` invalidation also still depend on v1. **Fix:** specify live compatibility persistence, including stable segment identities, or move debug sync and previews to v2. Test a new AG-UI-only thread without a legacy renderer saving it.

3. **Major — §11.3a applies turn-level deliverable rules to one `UIMessage`.** The agent spec assigns separate IDs to successive pi assistant messages, and the AI clone’s processor preserves those messages separately. The old renderer applies `turnDeliverables` across the whole turn. A write in one tool round followed by `present_deliverable` in another would now produce an extra fallback card instead of the final curated list. **Fix:** derive deliverables across the run’s messages and render the resulting card once. Test multiple assistant messages within one run.

4. **Major — §11.3a says any settled `present_deliverable` suppresses fallback files.** [The old implementation](/Users/rajaniraiyn/work/abacusai-bot/apps/desktop/src/renderer/components/chat/deliverables.ts) suppresses fallback only when explicit presentation produces at least one accepted deliverable: `if (out.length > 0) return out`. A completed presentation with no accepted paths must still show eligible writes. **Fix:** base precedence on the nonempty accepted list. Add an empty-presentation-plus-valid-write case for live and migrated parts.

5. **Major — §11.4 and R3-T32 resume a connector request too early.** They specify Connect or Submit fields followed by `connectors.respond`. The old [ConnectorRequestCard](/Users/rajaniraiyn/work/abacusai-bot/apps/desktop/src/renderer/components/chat/connector-request-card.tsx) awaits `refreshMcpServers` before answering “connected.” Main’s connect and respond handlers do not perform that refresh. The resumed agent can immediately call a connector tool absent from its tool list. **Fix:** refresh the requesting session’s MCP servers before responding, with refresh failures handled explicitly. Test the next tool call, not merely that the turn resumes.

6. **Major — §11.3’s silent-message predicate drops subagent-only messages.** It returns null when there is no text, file/artifact or notice part, even when a subagent part is present. The old `spokenItems` explicitly retains subtasks, and P55 promises their live narration and completed reports. **Fix:** include subagent content in the visibility predicate and define the bot-specific part whitelist. Test a delegation turn with no parent prose or deliverables.

7. **Major — §6.7 treats DB snapshots as a lossless completion stream.** `TableFeed.notify()` coalesces changes until `setImmediate`. A fast background run can change from idle to busy to idle before a diff, so the renderer never observes the required busy-to-idle transition. Recovery snapshots also cannot reconstruct it. The old unread path consumes `turn_complete` events. **Fix:** drive completion-based unread updates from the lossless run-completion notice. Test a complete run within one feed scheduling interval and completion during collection resynchronization.

8. **Major — §24.11 does not define a reliable terminal for its once-only completion notice.** It says “compat taps (turn end),” but compat `turn_complete` occurs after tool rounds, and `service-host.ts` explicitly allows an error after idle has provisionally completed a routine. Publishing at either point can produce premature success or duplicate completion. §17 also requires uncached failures to produce cues without identifying a source beyond `RUN_ERROR`. **Fix:** publish from the authoritative relay terminal, distinguish command errors from run failures, and consume its outcome for background failure cues. Test multiple tool rounds and idle followed by a terminal error.

9. **Major — §§13.2 and 13.4 resolve different models for App default.** The display resolver rejects an unconfigured stored default and chooses a runnable fallback. Main’s prescribed callback remains `readSettings().defaultModel ?? cachedRecommendedModelId()`, which accepts that unconfigured ID. The chip can display one model while main pins and attempts another. **Fix:** share one configured-model resolver between display and execution. Test a removed credential and a stored model missing from the catalog.

10. **Major — §13.4’s repinning misses changes to the app default.** A bot with `model: null` has an explicit effective model persisted on its sessions. Changing the app default does not change `bot.model`, and `openChatOnce` can return its cached handle without reaching main’s reused-session repinning. The displayed default can change while the next reply still uses the old pin. **Fix:** propagate default changes to null-model bots, or resolve their effective model at admission/start. Test a cached bot whose agent is stopped when the global default changes.

11. **Major — §12.1 exposes a forbidden model mutation for channel bots.** It hides “Edit bot” and Delete, but leaves the Model row actionable; §13.3 says that row edits `bot.model`. `ServiceHost.updateBot` rejects every channel-bot update. This contradicts §6.5’s assertion that channel-bot failures are prevented by the UI. **Fix:** make that row read-only for channel bots, or explicitly authorize and implement a narrower model mutation. Extend the channel-bot panel test to exercise the row.

12. **Major — §5.1’s sender-chat loader does not check that the bot exists.** Deleting a bot removes sender routing entries but retains transcripts and session owner stamps. An old sender session therefore still satisfies the loader’s `owner.botId` predicate after deletion, despite §5.5 promising the deleted view. **Fix:** require the bot row before accepting the session, and handle live bot/session removal on sender routes. Test a retained sender session after deleting its bot.

13. **Major — §11.1 leaves bot Markdown file links disconnected from the restored preview flow.** It passes `workspaceRoot={null}` and no `onOpenFile`. Under chat-kit §7.5, relative file links remain unresolved, while absolute file links fall back to Show in folder. The old Markdown renderer resolves paths and opens previews. **Fix:** pass the current session’s workspace root and the same preview callback used by deliverable rows. Test Markdown links in forever, sender and check-in sessions with different workspace roots.

14. **Major — §9.4 adds failure-prone readiness work after creation without defining recovery.** The bot and possibly its check-in are already persisted before `openChatOnce` or hydration can reject. Keeping the draft and retrying the create pipeline attempts another insert; the specified conflict recovery can mint a second bot. R3-T17 covers only successful readiness. **Fix:** record the completed creation stages, then retry opening/hydration independently or navigate to the existing bot’s error view. Test rejection after bot persistence and after check-in persistence.

15. **Minor — §13.1’s null App-default value conflicts with the chat-kit binding.** Chat-kit §8.2 declares `ModelChipBinding.value: string`, while this spec requires all model surfaces to use `null`. §24.2 does not amend that contract. **Fix:** make picker values and callbacks consistently nullable, or define a UI sentinel converted to null at the bot mutation boundary. Type-check the actual binding.

16. **Minor — §14.5’s 15% foreground outline does not establish the claimed accessible control boundary.** Mixing a dark foreground at 15% against white produces a boundary below 3:1, while the spec already establishes that every palette fill is below 3:1 against white. Testing that the outline exists does not test its contrast. **Fix:** use a sufficiently contrasting control border and assert the composited border-to-background ratio.

17. **Minor — §§7.2–7.3 cannot guarantee stable row instances merely by using bot-ID keys.** Moving a bot between separate Needs-you, Pinned and ordinary group parents remounts its row; React keys preserve identity only within the same parent. This also undermines the specified reorder animation. **Fix:** keep bot rows under one stable keyed parent with group-label rows, or explicitly permit remounting and revise the animation requirement. Test a bot entering and leaving Needs you.
