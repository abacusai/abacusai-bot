## Fix log

Evidence and the reasons behind fixes that differ from a review's proposal. No finding is rebutted.

- **Codex #1: the eager drain is real (verified in `node_modules/@orpc/*` 1.15.4).** `experimental_ServerPeerWithoutCodec.response` sends the response, then `resolveEventIterator(iterator, send)`, whose loop calls `iterator.next()` again as soon as `send` resolves; `MessagePortHandler`'s `send` is `postMessage`, which resolves at once. The client's `experimental_ClientPeerWithoutCodec.message` pushes every `EVENT_ITERATOR` message into `serverEventIteratorQueue` (`AsyncIdQueue`, an unbounded array per id) whether or not anyone pulls. `flow-control.test.ts` reproduces it through the real adapters: 20,001 event messages cross the port with zero `next()` calls, and main's queue never sees a backlog.
  - *Why credits at the interceptor level rather than in the port:* the port cannot see consumption, only arrival; the consumer's `next()` is visible only above the link's decode (`clientInterceptors`' lazy `body()` is decoded by `StandardRPCSerializer` into `mapEventIterator`, which pulls our wrapper exactly when the consumer pulls). On main, oRPC offers no async hook between iterator events except the pull itself, so the gate is a wrapper around the response body in a handler `interceptors` entry (it sees the request headers and the connection's context). The flow id travels as a request header, which the peer protocol preserves (`serializeRequestMessage` keeps `h`).
  - *Why the WebSocket transport is ungated:* it is development-only (A.8) and sends no header; the gate engages only with a header and a registry.
- **Codex #2: the HTML behaviour, checked in Chromium.** With the fix disabled, A-T12's page reports `closeOutcome: "hung"` for a pending call after a local `close()`; with it, `"rejected"`. Node's `MessagePort` fires `close` on both ends, which is why the renderer-next test uses a port that drops its own close events.
- **Codex #5: replay instead of negotiating before start.** The review offered either. Negotiating the subscription before capture would change `devices.stream.start`'s shape and still lose the key frame on every reopen after `RESYNC_REQUIRED`; recording the current group of pictures from capture start covers the first subscriber, late subscribers and reopens with one mechanism. Every producer prefixes key frames with SPS/PPS (`android-scrcpy-service.ts` concatenates `codecConfig`, `device-stream-service.ts` pushes SPS/PPS before type-5 NALs; MJPEG frames are all key frames), so a group that starts on a key frame is decodable.
- **Codex #6, Claude #2: a typed `retired` chunk rather than a synthetic `exit`.** A closed terminal's PTY is killed, so `exit` with null code would be arguable, but a promotion leaves the shell running under a new key and generation; reporting that as an exit would tell the renderer the shell died. The retirement is bus-only (`terminal-retired`), so the legacy `IpcEvent` stream is unchanged, and `LEGACY_EVENT_MAP` needs no entry.
- **Codex #8: a shared constant and an error class, not new result fields.** Adding a `code` to `SwitchWorkspaceResult`/`RelocateWorkspaceResult` would change what legacy IPC returns. `WORKSPACE_NOT_FOUND` is the exact string the service already returned, and `EntityNotFoundError` keeps the plain `Error` name, so Electron's rejection text for the old renderer is identical (`"Error: This routine is gone."`, pinned by a test).
- **Claude #4: why the commit handler checks the port at navigation start.** Closing on `did-navigate` alone could close the *new* document's port if its `rpc:connect` were processed before main handled the commit. The handler closes only the port that was active at `did-start-navigation`, and only if it is still active; a new document's connect already closes the old port itself (A.4.2's one-port rule).
- **Claude #6: `SwapAborted` keeps its immediate reschedule.** Only the `SwapNotReady` path (dormant until `FOUNDATION_API >= 2`) is deferred; an aborted swap was stood down by activity, so rescheduling at once just starts idle polling, which is the existing behaviour.
- **Codex #7, Claude #5: fan-out rather than a re-publish at the flip.** Publishing to every registered view keeps a candidate current during the whole wait, with no extra ordering between the flip and the publish.
