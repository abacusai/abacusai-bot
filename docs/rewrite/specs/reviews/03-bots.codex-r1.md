1. **Major — §5.3 assumes parent-loader completion.** The comment “layout already preloaded bots” is false: Router runs matched loaders concurrently (`refs/router/packages/router-core/src/load-client.ts:1023`). A cold `/bots/$botId` navigation can read the lazy collection before its snapshot arrives and incorrectly throw `notFound`; the editor has the same dependency. **Fix:** await `botsCollection.preload()` in each reading loader, or preload in serial `beforeLoad`. Test direct navigation with a delayed snapshot.

2. **Major — §13.4 and §24.7 retain the wrong model after choosing App default.** `BotService.update` repins only non-null models (`bot-service.ts:257`), while the renderer calls `agent.setModel` only when running. Resetting a stopped bot to `model: null` leaves its explicit session model intact; §24.7 starts the next reply with that stale pin. Existing sender sessions also return before repinning, contrary to “re-pin at their next start.” **Fix:** resolve and persist the effective bot model in main, including null resets and reused sender sessions. Test stopped-session resets through the real start handler.

3. **Major — The check-in session mapping describes sessions main does not create.** §§6.1, 6.6, 11.5 and 17 identify check-in runs through `owner.botId` and `owner.role === "routine"`. Actual scheduled runs are created with `routineId = job.id` and `owner: null` (`service-host.ts:3848`). Their activity, markers, files and completion cues therefore disappear from the proposed bot queries. **Fix:** join sessions by `routineId` to the bot’s exact-prompt check-in routine and specify their navigation. R3-T31 must fire a check-in and inspect its resulting session, rather than merely assert that the routine exists.

4. **Major — §10.2’s Paused switch cannot persist under §10.3.** `CheckInDraft` contains no enabled state; an unchanged schedule sends nothing, and a changed schedule forcibly writes `enabled: true`. Pause-only saves disappear, while editing a paused schedule resumes it. **Fix:** carry enabled state, compare it independently of the schedule, and preserve the selected pause state during schedule edits. Add pause-only, resume-only and paused-schedule-change tests.

5. **Major — §9.3’s schema transformations do not transform submitted values.** TanStack Form 1.33.5’s `standardSchemaValidator.js` discards successful schema output. Consequently `v.trim()` validates trimmed text but `onSubmit` receives raw text. Whitespace-only Instructions pass validation, remain truthy in `instructions || NAME_ONLY_MISSION`, then fail main’s empty-description check. **Fix:** explicitly parse the schema on submit and persist its output. Test whitespace-only Instructions for both create and edit.

6. **Major — §6.4’s remote synchronization marks untouched fields touched.** In installed Form 1.33.5, `setFieldValue(..., { dontUpdateMeta: true })` still validates; `validateField` marks mounted fields touched (`FormApi.js:209–217,647–675`). After one remote update, subsequent updates stop refreshing those fields. Blur-without-edit also becomes incorrectly protected from synchronization. **Fix:** disable validation and listeners during remote synchronization and distinguish actual user edits from touch metadata. Test two successive remote changes and blur without modification.

7. **Major — §§9.3 and 14.3 disagree about valid existing colors.** `resolveLook` preserves contrast-compliant custom hex colors, but `BotFormSchema.look.color` permits only `AVATAR_PALETTE`. Such an existing bot cannot save an unrelated name or mission edit. **Fix:** accept supported custom colors in the form schema and preserve untouched values. Add an unrelated-edit test using a custom-color bot.

8. **Major — §6.4 uses the wrong implemented prefs API.** `updatePrefs((p) => toggle(...))` supplies a recipe, but `renderer-next/data/db` accepts a `PrefsPatch`; transport B’s implementation notes document that contract. Foundation’s recipe description is stale, and §24 does not reconcile it. **Fix:** send patches such as `{ pinned: { botIds: next } }`, amend foundation, and preserve explicit same-value writes for provenance.

9. **Major — §11.3 changes ordinary emoji replies into reactions.** The old `message-reactions.tsx` derives badges exclusively from successful `react_to_message` results. An ordinary emoji-only assistant reply remains a bubble; suppression compares reply text against an actual tool reaction. **Fix:** port that derivation and its streaming behavior. Test emoji replies without a reaction tool, plus failed and rejected reaction calls.

10. **Major — §11.3 drops deliverable-selection rules while claiming P53 parity.** Old `deliverables.ts` gives successful `present_deliverable` results precedence, deduplicates paths, excludes unsettled/rejected calls, and filters fallback source-code and scratch files. Generic “file/document/image outputs” does not preserve those rules. **Fix:** specify equivalent derivation from live and migrated parts and test explicit-presentation precedence, duplicates, rejected calls and scratch files.

11. **Major — §11.3 changes deliverable opening and mishandles URLs and relative paths.** The old `deliverables-pill.tsx:43–59` resolves workspace-relative paths, distinguishes URLs, opens read-only previews, and offers Reveal/Open in browser. Sending every item to `system.openPath` loses these behaviors. PLAN removes the editor, not read-only previews. **Fix:** preserve path resolution, URL dispatch, preview and secondary actions, with tests for URLs, relative paths and guest workspace paths.

12. **Major — P63 claims connector-request parity that §11.4 defers.** The old `chat-panel.tsx:2228` renders an actionable `ConnectorRequestCard` while an agent tool waits for connection. §11.4 provides only the paused-check-in banner and says “nothing else in phase 3.” This is distinct from the decorative disconnected-connector banner deferred in §25.3. **Fix:** implement pending connector requests, reconnect snapshots and their response actions in this phase. Test that completing the connection releases the suspended turn.

13. **Major — §24.7’s feedback amendment does not establish usable feedback identity.** Accepting a live UIMessage ID is insufficient. `FeedbackService.submit` flushes legacy debug sync and resolves `sequenceOf(sessionId, segmentId)` before posting an uploaded `event_sequence_number`. Without a mapping, live IDs still produce `not-synced`. **Fix:** specify a persistent mapping from live message IDs to uploaded event sequences, or extend the uploader. Test the actual outgoing feedback payload through both services.

14. **Major — §6.6 replaces aggregate permission counts with one thread’s descriptors.** When the forever thread is cached, its descriptor count replaces the count across all bot sessions. A cached forever thread with zero requests can therefore display zero while a sender session waits; multiple waiting sessions also become undercounted. **Fix:** aggregate per session, substituting descriptor counts only for the corresponding cached session. Test simultaneous forever and sender requests, including a cached forever thread with none.

15. **Major — §14.4’s hash can index shapes with a negative number.** Although `h` is made unsigned, `(h >> 4)` converts it back to a signed integer. For `"Assistant"`, the specified hash is `3433796286`, and JavaScript evaluates `(h >> 4) % 16` to `-5`, yielding no shape. **Fix:** use `h >>> 4` and test names whose hash has its high bit set.

16. **Major — §17 lacks the data needed for background received cues.** Its trigger requires a completed run containing assistant text, but `SessionRow.turn` exposes only phase, busy state and timestamp. The additional chat stream covers the open thread, while uncached background threads have no message subscription. The proposed watcher cannot distinguish a spoken reply from a silent run for those bots. **Fix:** define a main-side completion notice carrying run identity and whether visible assistant output exists, or another explicit source covering uncached threads. Test a never-opened background bot and silent completions.

17. **Minor — §9.2 displays untouched-field errors on another field’s blur.** Form-level `onDynamic: BotFormSchema` validates the whole object and populates every invalid field’s metadata. Rendering `meta.errors` unconditionally contradicts R3-T10’s “blur shows that field’s error.” **Fix:** gate displayed errors on the field’s blur state or submission attempts. Test that blurring one field leaves other untouched fields’ errors hidden.

18. **Minor — §8.2 falsely calls typed-name precedence parity.** Old `new-bot-dialog.tsx:195–205` replaces the name with the translated template name when selecting a template. The spec and R3-T16 instead preserve the typed name, without an authorizing PLAN decision. **Fix:** retain template-name precedence or explicitly amend PLAN and mark the behavior Changed.

19. **Minor — §11.3 drops feedback availability gating.** Old `chat-panel.tsx:602` withholds feedback controls when there is no Abacus account. The spec offers them on every completed assistant bubble, including accounts for which main returns `no-key`. **Fix:** preserve account gating and test signed-out and signed-in states, or explicitly authorize the behavior change.

20. **Minor — §16.2 assumes the create identity survives slow navigation.** The destination loader awaits agent startup and chat hydration; after foundation’s 150 ms pending threshold, its skeleton can replace the setup avatar before the transcript avatar mounts. Those named boundaries then do not disappear and appear in the same commit, so the promised pairing fails. **Fix:** preserve the source until readiness or provide a matching pending identity. Extend R3-T26 with startup and hydration delays beyond the pending threshold.

21. **Minor — R3-T9’s oracle is removed by §24.9.** The test must read old-source literals, but the amendment replaces those literals with shared re-exports. After migration, that independent comparison cannot run as specified. **Fix:** capture immutable pre-migration fixtures for the prompts and announcement strings, then test both legacy exports and shared helpers against them.
