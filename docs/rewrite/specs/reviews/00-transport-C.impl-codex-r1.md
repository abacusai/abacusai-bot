1. **Major — [runner.ts:188](/Users/rajaniraiyn/work/abacusai-bot/apps/desktop/src/main/migrations/runner.ts:188).** Rollback deletes the backup directory before deleting the journal. A SIGKILL during that deletion, or before `removeStaging`, leaves a journal requiring backups that no longer exist. Every subsequent launch fails recovery permanently. The same ordering occurs at line 327. **Fix:** after successfully undoing all operations, unlink the journal before deleting backups, or atomically persist a terminal rollback state first.

2. **Major — [backup.ts:93](/Users/rajaniraiyn/work/abacusai-bot/apps/desktop/src/main/migrations/backup.ts:93).** The `EXDEV` fallback publishes the destination through a temporary-file rename, then unlinks the staged source. A SIGKILL between those operations leaves the destination changed, the staged source present, and `done` unchanged. `undoCommit` therefore skips the write. I reproduced recovery retaining `"NEW"` instead of restoring `"OLD"`. **Fix:** journal write intent before publishing the destination, and make rollback handle that intent even while the source exists.

3. **Blocker — [runner.ts:171](/Users/rajaniraiyn/work/abacusai-bot/apps/desktop/src/main/migrations/runner.ts:171).** A corrupt journal is treated like an attempt that never committed. Its staging is deleted without undoing published writes or restoring removals. A subsequent successful run can prune the orphaned backup, deleting the only remaining copy of a removed legacy file. The test at `runner.test.ts:381` explicitly expects this unsafe behavior. **Fix:** preserve corrupt journals, staging, and associated backups; record a recovery failure and stop migration writes. Pruning must exclude unresolved attempts.

4. **Blocker — [journal.ts:51](/Users/rajaniraiyn/work/abacusai-bot/apps/desktop/src/main/migrations/journal.ts:51).** Journal validation checks only the outer fields and whether three properties are arrays. It accepts unsupported versions and malformed write entries. An unknown `kind`, or a `replace-user` entry with an omitted backup, reaches `rmSync(write.dest)` and deletes user data. An in-memory reproduction with `version: 999` and a corrupted kind deleted the destination. **Fix:** validate the complete journal, including version, operation enums, backup requirements, paths, and `done` membership, before performing any mutation. Preserve invalid journals for recovery.

5. **Major — [runner.ts:178](/Users/rajaniraiyn/work/abacusai-bot/apps/desktop/src/main/migrations/runner.ts:178).** Recovery identifies a completed commit using only its millisecond timestamp. Two steps can receive the same stamp. If the second crashes, the first step's applied entry makes recovery incorrectly discard the second step's journal as `"finished"`. This reproduces with a fixed `now`: step 2 remains published while only step 1 is recorded. **Fix:** give every attempt a unique identifier and match both step identity and attempt identity.

6. **Major — [runner.ts:124](/Users/rajaniraiyn/work/abacusai-bot/apps/desktop/src/main/migrations/runner.ts:124).** `--rerun-migration` removes applied entries before recovery examines surviving journals. If a completed commit's staging cleanup failed, rerunning deletes its completion evidence and causes recovery to undo an already-applied migration. That can restore old prefs over subsequent user choices. **Fix:** finish recovery against the original record before removing IDs for rerun. Rerunning must re-plan from current files.

7. **Major — [record.ts:67](/Users/rajaniraiyn/work/abacusai-bot/apps/desktop/src/main/migrations/record.ts:67).** Treating a corrupt record as empty is unsafe when a completed commit's journal survives. Recovery interprets the absent applied entry as an interrupted commit and restores its old backup, potentially erasing newer user-provenance prefs. Idempotent re-planning does not make this rollback safe. **Fix:** distinguish an untrustworthy record from an empty one. With outstanding journals and an untrustworthy record, preserve the files and require recovery evidence before undoing anything.

8. **Major — [index.ts:1685](/Users/rajaniraiyn/work/abacusai-bot/apps/desktop/src/main/index.ts:1685).** Startup ignores whether recovery remains unresolved and installs writable prefs consumers. After a transient rollback failure, the UI can save new user-provenance choices; the next successful recovery restores the pre-migration backup over those choices. I reproduced `"USER CHOICE"` being replaced by `"OLD"` after a transient restore failure. **Fix:** return unresolved destinations from the runner and prevent writes to them, using an in-memory fallback or separate overlay until recovery finishes. Keep ordinary startup available.

9. **Major — [journal.ts:71](/Users/rajaniraiyn/work/abacusai-bot/apps/desktop/src/main/migrations/journal.ts:71).** Every journal read error becomes `"missing"`, including `EACCES` and `EIO`. Recovery may consequently unlink an existing unreadable journal without restoring anything. Likewise, `runner.ts:164` treats every staging-directory enumeration error as “no attempts,” allowing migration execution without completing recovery. **Fix:** recognize only genuine absence as missing; propagate other errors, preserve recovery files, and stop migration mutations.

10. **Major — [journal.ts:125](/Users/rajaniraiyn/work/abacusai-bot/apps/desktop/src/main/migrations/journal.ts:125).** Removal recovery silently succeeds when both the original and its backup are absent. Unlike `replace-user` recovery, it never reports the missing restoration source. The runner then deletes the journal and records recovery as successful despite losing a legacy file. **Fix:** when a removal was completed and neither copy exists, fail recovery and retain the journal. Journal removal rollback completion so repeated recovery can distinguish an already-restored operation.

11. **Minor — [runner.test.ts:229](/Users/rajaniraiyn/work/abacusai-bot/apps/desktop/src/main/migrations/runner.test.ts:229).** Crash hooks run after journal updates or before the record; they miss the failing boundaries above. Add filesystem-level kill injection covering every transition, with these expected outcomes:

    - Backup temporary-file rename: only an orphan backup before the initial journal; destinations remain untouched.
    - Initial journal rename: discard staging before publication; recover the attempt after publication.
    - Same-volume staged-file rename, then `done` journal rename: recover even between them, using the missing staged file.
    - Cross-volume destination temporary-file rename, then source unlink, then `done` journal rename: recover at all three boundaries, including the currently broken first gap.
    - Removal rename into backup, or cross-volume copy publication and source unlink, then journal update: restore the original.
    - Record rename: undo before publication; retain committed output afterward.
    - Successful journal unlink, then staging deletion: retain committed output across either interruption.
    - Rollback restore rename, created-file unlink, and removal restore rename: repeat rollback safely.
    - Rollback backup deletion, then journal unlink: currently leaves recovery permanently broken.

    The tests also need interrupted recovery, equal timestamps across steps, malformed journals, and pending-journal backup pruning.
