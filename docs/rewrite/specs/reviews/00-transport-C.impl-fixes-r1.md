# Spec 00 sub-slice C: fixes after implementation review r1

Sources: `00-transport-C.impl-codex-r1.md` (X1–X11) and `00-transport-C.impl-claude-r1.md` (L1–L19, with its W0–W14 crash-window table). Overlapping findings are fixed once and listed together. Two follow-up items from the step-1 reviews (`00-transport-C1.impl-codex-r1.md` #4, `00-transport-C1.impl-claude-r1.md` #15) are included at the end, because they concern the runner.

The design rule: recovery must be safe at every crash window, and that is proved by a filesystem-level kill harness (`runner.crash.test.ts`), not argued. Every mutating filesystem call the runner makes now goes through `MigrationIo`. The harness kills the process at each call in turn (a write, append or copy leaves a torn prefix, and nothing after it takes effect), then asserts what the next launch does. It covers a full commit that exercises every write kind and removals in two "volumes", same-volume and with EXDEV, a commit whose in-launch undo dies, and a recovery killed once and twice. It found one defect of its own, listed under X11.

Commits (worktree branch, on top of `446b38a0`):

1. `f48a4b59` Migrations: attempt-id journal, append-only log, safe rollback order, unresolved attempts
2. `097584d8` Migrations: filesystem-level kill harness over every commit and recovery transition
3. `99c0abda` Migrations: uncloseable progress window, theme from legacy state, write-blocking API
4. `d00a6a16` Merge `rewrite/renderer` (sub-slice B fixes, steps 1 and 4, `plan.pending`)
5. `f53d14f1` Startup: hold prefs.json while a commit is unresolved; dispose the progress window on failure and quit
6. `64b102aa` Legacy prefs: old-UI validation for onboarding and homepage, per-member invalidity, zustand version, unreadable renderer-state fails step 2
7. `021a3623` Migrations: durable partial-commit record with a stall cap; Electron-free write-block predicate
8. (docs) Spec C notes and this log

"Red" is not claimed per test. The runner's interfaces changed (journal v2, `MigrationIo`, `unresolved`), so the new runner tests cannot run against the old code. The harness reproduces the reviewed failures by construction: the W3b EXDEV window, the W10/W11 deletion order, and a corrupt journal are among its kill points or cases.

## Crash safety and recovery (`runner.ts`, `journal.ts`, `backup.ts`, `record.ts`)

| Finding | Fix | Test |
|---|---|---|
| X1, L1 (backups deleted before the journal wedge recovery for good; W10, W11) | A rollback now deletes the journal first, then the backup directory, then the staging. Once the journal is gone the attempt is over, and a leftover backup directory is an orphan that is pruned by age. The "backup missing" refusal is also no longer a dead end when the file is already right. The rollback judges a `replace-user` destination by content (sha256 of the original and of the staged file, both in the journal). If it equals the original, there is nothing to do, and the backup is not needed. Each rollback operation also appends `undone` to the log, so a repeat skips it. | Harness: recovery killed at every call, once and twice, and the journal `rm` is asserted to precede the backup `rm`. `runner.test.ts`: "recovers when the missing-backup case is already restored (no permanent dead end)". |
| X2, L2 (EXDEV: destination published, staged source not yet unlinked, so recovery keeps the new content and deletes the only backup; W3b) | The rollback no longer asks whether a move happened. Every rule is correct either way. A `create` is deleted (it did not exist when the commit began). A `replace-derived` is kept. A `replace-user` is judged by content, as above. A removal is moved back when the original is gone. The window therefore needs no log entry. The staged-file-gone heuristic is removed. | Harness, cross-volume: the kill points include `rename userdata/state.json.migrating-tmp -> userdata/state.json`, then `rm …/3.out`, then the log append. Recovery gives `STATE-OLD` at each of them. `runner.test.ts`: "undoes by rule when no done line was written". |
| X3, L3 (corrupt journal discards staging without undoing; its backup is later pruned) | A journal that is not valid JSON, or does not validate, is **unresolved**. The staging, journal and backups stay as they are, `lastFailure` is recorded, no step runs and nothing is pruned. Because its destinations are unknown, every destination is blocked (below). | `runner.test.ts` "keeps a corrupt journal, its staging and its backups, and blocks every destination" (a launch 14 months later still keeps the backup). |
| X4 (validation checks only the outer fields; `version: 999` or a bad kind reaches `rmSync(dest)`) | `validateJournal` checks the whole journal before recovery touches anything, and every journal is read before any is acted on. It checks: version 2; the attempt id; that the step matches its staging's name; the stamp; that the backup directory is exactly this attempt's; each write's destination (absolute, normalised, under the home or userData, never the runner's own files); its staged path (inside the staging, used once); its kind; that its backup is exactly `backupPathFor(dest)` for `replace-user` and null otherwise, with both hashes; each removal's backup; no path touched twice; and every log line (this attempt's, a valid op and target, an index in range). | `runner.test.ts` "keeps a journal with …, touching nothing" × 7 (unsupported version, unknown kind, `replace-user` without backup, destination outside the home, foreign backup directory, no attempt, step not matching its staging): the whole temp tree is byte-identical afterwards. Also "a malformed line before its end". |
| X5, L9 (finished commit matched on the stamp alone) | Each attempt has a random id. The journal, every log line, the backup directory name (`<stamp>_<attempt>-<id>-<name>`) and the record entry all carry it. A journal counts as finished only when the record holds its **step and attempt**, or its log has `recorded`. | `runner.test.ts` "tells two steps committed in the same millisecond apart by attempt" (a fixed clock, step 2 crashes, and it is undone while step 1 stays). |
| X6, L10, W14 (`--rerun-migration` before recovery undoes a finished commit) | Rerun is applied after recovery, against the original record. The step then re-plans from the current files. | `runner.test.ts` "finishes recovery against the original record before --rerun-migration": the file is not rolled back to `OLD`, and the new backup holds the post-commit content. |
| X7 (corrupt record read as empty, so recovery undoes a finished commit) | `readRecordState` tells apart `missing`, `ok`, `corrupt`, `unreadable` and `newer`. Suppose the record cannot be trusted and an unfinished journal has no `recorded` line: whether the commit finished is unknown, so the attempt is unresolved and nothing is touched. A `recorded` line in the log is proof on its own. A corrupt record with nothing pending is kept as `migrations.json.corrupt-<stamp>`, and the idempotent steps run again. | `runner.test.ts` "with a corrupt record and an interrupted commit, keeps everything", "finishes a recorded commit by its log line even when the record is corrupt", "sets a corrupt record aside…". |
| X8, L4 (writable prefs during unresolved recovery; the next recovery restores the backup over the user's new choices) | Two layers. (1) Writers are kept off unresolved destinations. `RunMigrationsResult.unresolved` lists them, and `write-block.ts` holds them for the launch (`isMigrationWriteBlocked(file)`). `index.ts` swaps `PrefsStore` onto a session-only copy in the temp directory when `prefs.json` is blocked (`prefsFileAfterMigrations`), so the app starts and works. The live legacy sync goes through the same store. (2) The rollback itself never overwrites a `replace-user` destination whose content is neither the original nor what the commit staged: it keeps it and logs. | `startup.test.ts` "serves prefs from a session copy only while an unresolved commit covers prefs.json"; `runner.test.ts` "keeps an unresolved attempt, blocks its destinations…" and "keeps a user file changed after the commit rather than restoring over it"; the `write-block` test. |
| X9, L3 (every journal read error is "missing"; a staging-list error means "no attempts") | Only ENOENT and ENOTDIR count as absent: `exists`, `readJournal`, the log read, the record read and the `.migrating` listing. Any other read error makes the attempt (or, for the listing, everything) unresolved. | `runner.test.ts` "keeps a journal it cannot read" (EACCES injected), "runs nothing when .migrating cannot be listed" (EIO injected), "runs nothing when the record cannot be read". |
| X10 (a removal with both copies missing succeeds silently) | The rollback throws, and the attempt is unresolved and kept, unless the log says this rollback already restored that removal (`undone`), which means something else deleted the file afterwards. | `runner.test.ts` "keeps the journal when a removed file and its backup are both gone". |
| X11, L19 (crash hooks miss the failing boundaries; missing tests) | The kill harness `runner.crash.test.ts` covers every transition in X11: the backup temp-file rename; the journal temp rename; the staged rename then the log append; EXDEV's destination temp rename, source unlink and log append; a removal's rename, or its EXDEV copy then unlink; the record rename; the journal unlink then the staging `rm`; the rollback's restore rename, created-file unlink and removal restore rename; and the rollback's journal unlink then backup `rm`. The expected outcome is asserted at each: before the record rename, rolled back; after it, committed; nothing unresolved; no `*.migrating-tmp` left beside user files; the next launch finishes the step with a backup holding every original. The other gaps: interrupted recovery (killed once and twice), equal timestamps, malformed journals, and pruning with a pending journal (the corrupt-journal test) are tested above. The harness found a defect of its own: a torn log line, followed by a rollback's append, became a malformed line in the middle of the log, which made the journal invalid. A rollback now trims a torn tail before appending. | `runner.crash.test.ts` (6 tests, 3 per volume mode, about 250 kill points in total). |
| L5 (journal rewritten in full after every move, about 1.2 GB for 2k files; synchronous commit) | The journal is written once. Progress goes to the append-only `commit.log`, about 80 B a line. The commit loop and the rollback are `async`: they yield (`setImmediate`) every `yieldEvery` (20) moves and report progress for the commit phase, which gets the last 20% of a step's share. | `runner.test.ts` "writes the journal once and appends one done line per move" (45 files: one journal rename, 45 lines, commit-phase progress), "yields to the event loop during a large commit"; `progress-window.test.ts` "opens and updates during a long commit". |
| L7 (quarantine pruned by mtime, which a move keeps) | Partly rebutted, with a change. Step 4, now merged, quarantines by writing a fresh copy into staging, so the file's mtime is the quarantine time and mtime ageing is correct for it (`004-archive-transcripts-v1.test.ts` "keeps quarantined files 90 days" relies on it). For anything that is *moved* into quarantine, `quarantineDirFor(home, kind, stamp)` gives a stamped run directory, and pruning ages such a directory by its stamp, not by the mtimes inside it. | `runner.test.ts` "ages quarantine by its run's stamp, not the file's mtime" (a 400-day-old mtime inside a 1-day-old run is kept). |
| L8 (pruning never runs once everything is applied; `.migrating/` left empty) | Housekeeping (`rmdir .migrating`, pruning) runs at the end of every launch that got there without a failure, including one with nothing pending. | `runner.test.ts` pruning tests run with no steps; "undoes every kind…" asserts that `.migrating/` is gone. |
| L16 (record and journal version ignored) | A record `version` above 1 means the runner does nothing: no recovery, no step, no write. The journal requires version 2. The older format is invalid, so the attempt is kept as unresolved, not guessed at. | `runner.test.ts` "runs nothing and never writes a record from a newer build"; the `version: 999` journal case. |
| L18 nits | The temp name is fixed (`<dest>.migrating-tmp`), so each rollback operation sweeps it first. Pruning renames a directory to `.pruning-<name>` before `rm -r` and sweeps leftovers first. `validatePlan` rejects two writes that share one staged file, a staged path equal to the journal or log, and any destination or removal outside the home or userData, or inside `.migrating/`, `backups/migrations/` or `migrations.json`. Renames retry up to 4 times on Windows EPERM/EACCES/EBUSY. The note on the live sync's synchronous compose is recorded as a note only (no change). | `runner.test.ts` "plan validation" (3 tests), the pruning test (a `.pruning-*` leftover is swept), the harness's no-`.migrating-tmp` assertion. |

## Progress window and startup (`progress-window.ts`, `startup.ts`, `index.ts`)

| Finding | Fix | Test |
